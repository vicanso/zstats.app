# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

macOS menu-bar metrics panel: gpui-kit (gpui-pre snapshot + gpui-component) for the UI, the `zstats` crate (`frontend` feature, no tokio) for collection and alerting.

`docs/design.md` is the design record (README.md is the user-facing GitHub page, README-zh.md its Chinese twin — keep the pair in sync when editing either) — it explains *why* nearly every non-obvious decision here is the way it is (window reuse, Dock suppression, tray rasterisation, vibrancy layering, the multi-display workarounds). Read the relevant section before changing any of that machinery; the odd-looking code is usually load-bearing. `docs/cross-platform.md` is a hypothetical: what the panel would owe if zstats ever grew platform-aware capabilities — its first section (stop guessing whether a platform can produce a metric, read it) is worth doing on macOS alone, the rest is contingent on a port that has not been committed to.

## Commands

```bash
make dev      # cargo run (debug: opens the panel immediately, no auto-hide)
make debug    # RUST_LOG=debug cargo run
make check    # cargo check --all-targets
make lint     # cargo clippy --all-targets --all-features -- --deny=warnings
make test     # cargo test --workspace
make release  # cargo build --release
make bundle   # .app + writes LSUIElement into Info.plist (needs cargo-bundle)
```

**After every change set, run `make fmt` and then `make lint` before finishing.** CI runs `cargo fmt --check`, so one over-wide line that clippy and the tests never notice still fails the build — which has happened. `make lint` alone is not enough: clippy does not check formatting.

Single test: `cargo test <name>` (e.g. `cargo test anchored_origin`) — tests are inline `#[cfg(test)] mod tests` at the bottom of each module, not a `tests/` directory.

`ZSTATS_DEBUG_POSITION=1` prints the whole tray-anchor → window-origin conversion chain; use it for multi-display placement bugs.

Logs land in `~/.zstats/logs/zstats-app.log.<date>` (daily-rolling, 90-day prune; `logger.rs`, the zedis logger adapted). INFO by default, `RUST_LOG` overrides — `make debug` finally means something. The alert-class trail lives there: every reported `AlertEvent` with its banner verdict (delivered / snoozed / auto-quieted / muted), every quit/SIGTERM request, every move-to-Trash, both transitions of the tray's memory-recovery clock (started / reset, with how long it had run), both transitions of the keep-awake assertion, and every change in the launch-at-login status (`autostart::refresh` — the raw `SMAppService` state, sampled at launch, on settings-window open, and when that window becomes active again, logged only when it moves; the Interface row is a switch for `Enabled` / `notRegistered` only — `requiresApproval` is a sentence that opens Login Items, `notFound` is "needs the installed zstats.app", because `register` cannot win those) — at INFO because "the episode looks over, why is the menu bar still on memory?" is asked about the installed build, where DEBUG is not being captured. New failure paths use `tracing::warn!`/`error!`, never `eprintln!` — under LaunchServices stderr goes nowhere, which is how ~30 of those lines vanished for months (the two survivors are deliberate: logger's own bootstrap error, and `ZSTATS_DEBUG_POSITION`'s on-demand chain).

## Platform reality

macOS is the only **released** target; Linux builds and passes the suite on both architectures (`.github/workflows/test.yml`'s `linux` job, `ubuntu-latest` + `ubuntu-24.04-arm`) and is a port in progress, not a supported platform — every release now carries two Linux tarballs and `scripts/install-linux.sh`, labelled a preview in both READMEs, but most of the code has only ever been exercised in CI, which has no compositor, plus one Omarchy machine. The sentence that used to stand here — that the crate does not compile anywhere else, because six files `use` macOS-only modules unconditionally — stopped being true at `docs/omarchy-port.md` 阶段 0: the `compile_error!` is gone, `procscan` is split into `procscan/{mod,macos,linux}.rs`, and the gates reached those six files. Windows remains in the "never built" category. Linux now has a tray (`docs/omarchy-port.md` 阶段 3): `tray.rs` is no longer cfg'd out and `tray-icon` is declared twice, with `default-features = false, features = ["ksni"]` on Linux — StatusNotifierItem over D-Bus, no GTK loop, which is what the old exclusion was about. It needs an SNI host on the session bus and degrades to no icon without one — but not for the session: a login launch (the XDG autostart) can beat the bar that owns `org.kde.StatusNotifierWatcher`, and tray-icon spawns ksni without `assume_sni_available`, so that first registration fails hard (measured on Omarchy: `ServiceUnknown: The name is not activatable`, the whole session iconless). `tray::sni` parks a thread on the bus's `NameOwnerChanged` for that name (subscribe, then ask, so an appearance in between is not missed) and builds the tray when a host appears; after that ksni re-registers across bar restarts by itself. Two things zstats ≥ 0.6.1 fixed for Linux shape what the app shows there: threads are no longer listed as processes (they were each an alert subject and each carried their owner's RSS), and `systemd --user` bounds process trees the way pid 1 does, so each app a session launches is its own Apps row — `fullscan::tree_members` mirrors that boundary (`is_service_manager`), or expanding the manager's row would list every app it launched. Three things that path cannot do, all in `tray.rs`'s module doc: no icon rect (every anchor is `None`, the compositor places the panel), no right-click event (the host renders the menu; `secondary_activate` is a *middle* click), and no template images — so the glyph picks its own colour from the resolved theme (`tray::ink`), which is the one place a light panel theme in front of a dark bar can hide the icon. The missing title stays conceded: drawing the figure into the bitmap was tried and reverted — Quickshell fits a wide pixmap to the tray slot's width, which shrinks the glyph to nothing (`docs/omarchy-port.md` 阶段 3 says why not to try it again). One more thing that path taught: gpui-component's client-side frame must not wrap a layer surface — it calls `set_client_inset(20px)` every frame and gpui's Wayland backend adds that back into the committed buffer, so the surface paints 40px past the box the compositor anchored. Up to gpui-kit 0.6 the panel's `Root` was built `bordered(false)` on that path; 0.7 removed the option (longbridge/gpui-kit#3152 — the frame is now gpui-component's `Root` plugin, whose `decorate` wraps every window unless the platform reports `Decorations::Server`), and gpui reported a layer surface as client-decorated, so the fix moved into gpui: **`patches/gpui-pre-linux` is a vendored gpui-pre-linux 0.3.7 with two hunks** (grep `zstats-app patch` — a layer surface reports `Decorations::Server` and a zero inset), wired in by `[patch.crates-io]`. It must track the `gpui-pre` version: after any gpui bump, re-vendor that release and re-apply the hunks (or drop the patch if gpui has learned this itself), and `cargo tree -i gpui-pre-linux` must show the path source — a stale patch is either a second gpui identity or a silent return of the 40px panel. Beside it, `ipc.rs` (Linux-only) is the entry point that does *not* need a tray: one unix socket in `$XDG_RUNTIME_DIR` makes the process single-instance, so `zstats --toggle` from a compositor keybinding reaches the running panel instead of starting a second collector. It binds before it connects (the reverse order lets two simultaneous launches each delete the other's live socket) and has no `/tmp` fallback, because a single-instance lock another user can hold is worse than none. A bare launch and `--toggle` differ on one point that matters: with no instance running, a bare launch must *not* open the panel (that is the login path) and `--toggle` must. Since the 2026-09-23 audit the other Linux arms are real too, each with its own reason in its module doc: `updater.rs` installs the release tarball over the running binary and refuses a release without `SHA256SUMS` (nothing else vouches for the bytes there); `awake.rs` holds a logind idle inhibitor whose file descriptor *is* the hold; `autostart.rs` writes the XDG entry and shows a sentence, not a switch, in a session nothing reads it from; `bigfiles.rs` walks `$HOME` with `find`, trashes through `gio` and reveals through `FileManager1.ShowItems`; the disk eject goes through `udisksctl`; the alert cards keep their SIGTERM quit. The panel is 739 tall rather than 792 (`placement::DEFAULT_WINDOW_SIZE`, cfg'd). Overview's cards measured 489 on Omarchy against 543 on macOS before the three recent-readings charts — the Processor card's P/E rows, which zstats reports on macOS only — so the macOS height left 57 of empty panel; both heights then grew by 132 for those charts (40px plus 4px above each) and by 54 for the caption under each (14px plus 4px), and shrank by 61 when the apps card went from five rows to three (`overview::TOP_N`, measured from the Memory card's bottom edge), which keeps the same few pixels under Memory; both then grew by 14 when the disk/network rates and the network chart left the Memory card for a card of their own (`overview::io_card`). the Permissions page does not exist off macOS — the variant is gated, not just hidden. **Verifying a Linux arm from this Mac**: swap the file's `macos`/`linux` gates through a placeholder, `make lint` and `cargo test`, restore from a backup and diff — POSIX-only tests then run for real here; zbus-using code goes through a scratch crate checked for `x86_64-unknown-linux-gnu`. That is how four would-be Linux compile failures were caught before CI saw them. `docs/omarchy-port.md` is the phased plan and the audit record; still open there: `cleanhints-linux.toml` / `caches-linux.toml` (content, not code), a Hyprland IPC arm for `active.rs`, and two things only the machine can answer (the portal's colour-scheme default, hypridle honouring the inhibitor). Keep the untested branches for whoever ports this further, but do not describe them as supported or verified — every Linux phase so far is "compiles and tests pass in CI", never "seen working".

## Architecture

**One root view, one global store.** `views/` modules are plain functions that read `ZStatsGlobalStore` (a `Global` wrapper around `Entity<ZStatsAppState>`) and return elements — they are *not* gpui views. The whole panel repaints per tick. Anything that must survive hide → re-show goes in `state/`, including per-tab `ScrollHandle`s: disk analysis lives in `state/analysis.rs`, alert episodes in `state/alerts.rs`. gpui discards element state for anything not painted, and only the active tab is painted. The deliberate exception is query-like state — the name filter, the one-shot full listings, and the Apps expansion selection — which both hide paths reset via `reset_transient_views`: a panel reopened hours later with yesterday's query looks broken, not remembered. The selection is also a cost, not just a query: `ensure_apps_topology` keeps a selected tree's member table fresh every 15s ahead of its visibility gate, so a selection surviving hide kept full-table scans running tray-resident. The selected tab itself survives a restart too (`app.toml` `tab`), which is why tab-entry work — the History read, Hardware's once-a-minute `tmutil` probe, the Network tab's listening sockets, the topology fetch — keys off `panel_visible` rather than the selection, and `mark_panel_shown` runs it as a visit: a login launch that restored History or Hardware must not read or spawn for a panel nobody opened.

**Collection is a resident background thread** (`metrics.rs`) running `zstats::Monitor::tick()`, handing `Tick`s to the main thread over a `smol::channel`. It must outlive the window — `Monitor` holds the previous-sample baselines that every rate is diffed against. Cadence is adaptive (config `interval` when visible, 5s when hidden) and waits with `recv_timeout` so opening the panel samples immediately. First-sample rate metrics are legitimately `None` → UI shows `—`. Overview keeps thirty minutes of whole-machine CPU (`usage_percent`), memory `used_percent` and network download and upload — one ring per direction — in in-memory rings (`series.rs`), appended on every `ingest` including the 5s hidden tick. The network channel still refreshes on its own 15s cadence; ticks in between repeat the last rate, and an absent rate is a break in that direction's line. The network chart draws both on one ceiling: download in the full ink (the line most people read), upload behind it in `dim_ink` — it stays, because a backup or sync pushing out is as often why the network is busy, and the old ↓+↑ sum could not say which way a burst went. The rings survive hide and are not written out — zstats' minute history stays the durable record. Their windows are wall-clock time: `Instant` stops while the machine sleeps (macOS and Linux alike), which used to fold a night's lid-close out of the ring and leave last night's minutes — and their peak — joined onto the morning's; each tick compares wall-clock and `Instant` progress (`series::slept`, past `GAP`) and moves every earlier point back by the sleep (`Series::shift`, `traffic::CurveBook::shift`), so a sleep is a break of its real width and a long one starts the chart over. A ring is labelled full (`30m`, the traffic card's `10m`) once its oldest point is within `GAP` of the window — pruning keeps only points at most the window old, so the exact comparison read `29m` forever. Process-traffic's own curve stays ten minutes. The CPU and network strokes are monotone cubics through those samples, so a tick does not draw a corner at every reading and the line does not peak above a sample. A network rate that holds for its 15s refresh stays flat. Memory is bars on a fixed 0–100 axis, one per 30s slot, each the slot's average, a quarter of each slot left as the gap (`BAR_GAP_SHARE`); only the newest bar is full ink, the history `dim_ink` (`CHART_DIM`) — used% barely moves in half an hour, and sixty full-ink bars were the brightest block in the panel for the least news. CPU's top is 30 while every point stays at or under 30, and the next 10% step above the window's highest point once one goes over it (`CPU_AXIS_STEP` — the exact peak would print as "33.2%" and move on every new decimal); memory's top is a fixed 100; the network ceiling is 1 MiB/s while every point stays under it and doubles from there (`NET_SCALE_FLOOR` — the network's `CPU_AXIS_LOW`: a 64 KiB/s floor let everyday 100–300 kB/s swings rescale the line while the window filled; deliberately not the Network tab's per-program 64 KiB/s floor). The time axis is the full 30 minutes, so a short history stays on the right and the time before the first sample stays empty. Memory bars split that width into 60 equal slots of 30s; the curves stay 90 points of 20s. The CPU and network charts print their axis top in the well's top-left corner (`corner_label` — "40%", "8 MB/s"; the oldest end of the axis, so the newest data is never under it), because the top was otherwise a rule in a tooltip: 30% under a "Max 15.8%" caption, or an unnamed doubling under "Max 6.6 MB/s"; memory's is always 100% and stays unlabelled. Each chart sits on the recessed meter-track fill, with hairline guides at 10 and 20 minutes ago (`paint_guides`) from the first frame — before the window fills, the empty left of the well otherwise read as a chart that failed to draw. A hole *between* readings — the rings are fed on every tick, so it is the Mac asleep or the app not running — carries a dotted baseline (`paint_gaps`, the lead line only); bare, it read as a broken chart. Under it, one line: the highest point drawn — the 20s (bars: 30s) average, not the raw tick, so the figure is a height the line reaches; the raw max let a two-second spike name a peak nothing on the chart showed, which read as an all-time figure (↓ and ↑ for network, under a network glyph — the row above it carries disk rates with the same arrows) — and how long the window has been collecting. No "now": the latest reading is already the card's headline, the memory meter, or the rates row. The chart keeps the card width. The drawing averages that ring into at most 90 points, one per 20s slice, from the first sample on — not raw until the grid fills: at 2s, 90 samples are the newest tenth of the axis (~30px), and the switch at the 91st would drop the peaks and rescale both ceilings in one frame (`overview::bucketed`); the CPU top and the network ceiling read those averages. An empty slice between readings is a break. Each chart stays 40px, so a ceiling change moves the mark inside the slot and does not resize the card. **GPUs and physical drives are the one exception to "collect for the life of the process"** (zstats ≥ 0.5.8): zstats reads both through an `ioreg` child process at ~45 ms of CPU a read at this app's cadence (~66 ms for both — only 11-13 ms back to back, which is the figure zstats first documented), so its 10s defaults alone would roughly double the app's hidden-panel cost for figures nobody is reading. The collector thread therefore applies `Monitor::set_collect_gpu` / `set_collect_drives` before every tick, on only while the panel is visible *and* the selected tab displays them (`metrics::tab_reads_registry` — the single place that says which tabs those are; `CollectorPace::tab_selected` mirrors the tab, seeded in `metrics::start` because the session's tab is restored before the pace exists). A runtime switch, never a rebuild — a rebuild resets every other channel's baselines. The file's `collect-gpu` / `collect-drives` is a ceiling (`with_always_on` does not force them on like the other channels), but their cadence is ours: `PANEL_REGISTRY_INTERVAL` (5s) overrides the file, because a channel that runs only while someone looks is a live view — zstats' own foreground view reads both every beat — and the switch restarts drive rates from no baseline, so 10s meant ten seconds of `—` per visit. `fullscan.rs`'s one-shot collectors turn both off explicitly, because zstats defaults them on. Where they show: `views/drives.rs` and `views/gpu.rs`, on Hardware after the volumes (volumes answer "is it full", drives "is it slow" — two cards, never joined, since APFS puts several volumes on one drive; queue depth is printed as a number, never a 0-100 bar, because the driver has no busy-time clock). Only asking "is anyone reading this?" was right for these because nothing else consumes them: zstats has no GPU or drive rule and records neither in history, so background samples would be numbers nobody sees. Swap activity (`swap_ins_per_sec` etc.) is plain sysctls and always on; it shows on Overview's memory card only while segments are moving (`overview::swap_moving` — a settled machine gets no line, zstats' own pressure summary makes the same call), in the pressure alert's sentence, and `kernel_available_percent` is printed in the pressure badge itself ("Normal · 62% available" — the word stays, a bare percentage beside a memory card reads as used), beside the verdict it drives; the tooltip says why it is lower than free GB.

**Listening sockets are a panel-owned query, not collection** (zstats ≥ 0.6.0, `views/listening.rs`, `state::ensure_listeners`), and the Network tab's second card — under process traffic, ahead of the interfaces, which split a throughput Overview already shows and are often an empty state (then a header, its chip and one line, not a full empty card). `zstats::listeners()` is a one-shot function outside the snapshot — a listener list has no baseline and changes rarely — so the store calls it on Network-tab entry and every 15s while that tab is on screen (`LISTENERS_REFRESH`, same gates as Hardware's space probe), off the main thread, single-flight, and `reset_transient_views` drops it on hide (a late answer for a hidden panel is discarded). Measured ~3.4 ms of CPU a call for 86 sockets. **macOS names every socket's owner only to a process with an app-bundle identity**: a bare executable — every `cargo run` / `make dev` build — gets `CollectError::Restricted`, which the card shows as "needs the installed zstats.app" rather than a list of our own two sockets. To see the real card from a dev tree: `cargo bundle`, then `codesign --force --sign - <target>/debug/bundle/osx/zstats.app` (the linker's ad-hoc signature leaves Info.plist unbound, and it is the bound Info.plist that counts), then run the binary inside the bundle. Rows are process *names* (twenty `redis-server`s are one row, `×20`; the tooltip maps each endpoint to its pids), exposed-first (`*:port` = every interface, in the brighter ink — not accent, it is a fact rather than a crossed threshold), a hard preview cap of six TCP rows, UDP only when expanded (mDNS alone opens 5353 in most apps). Each row is two lines — who (name, pid or `×N`, and how long it has been up: zstats' `run_time_secs`, zstats ≥ 0.6.1, the largest unit only (`format::uptime_short`, as Overview's uptime — `11d`, not `11d 10h`), a newest–oldest range for `×N`, nothing for a process whose start the OS will not give) over where (the endpoints, with Quit at the end of that line; every second line is held to the button's height so rows with and without one match). The header's magnifier opens a search (`toggle_listen_filter` — the process filter's shape, closed and cleared on hide) over the whole answer, UDP included and uncapped: a name match keeps the row whole, otherwise only the matching endpoints stay (by label, by the addresses `*` / `localhost` stand for, by protocol word, or by an exact pid — a partial one would match half the table) and the `×N` narrows to their holders.

**Per-process traffic is the Network tab's other query, and its first card** (zstats ≥ 0.7.0, `zstats::process_traffic()`, `traffic.rs`, `views/traffic.rs`). Cumulative socket bytes, not a Tick field: the crate keeps nothing between calls and the rate is the client's diff (`traffic::diff` — per pid, only while `run_time_secs` still names the same process, no rate on first sighting, a counter that fell is `—` for that direction rather than a negative). Diff per pid *then* sum by program name, so one helper closing a connection does not cancel a sibling that is still transferring. Rows are programs (`×N`), ranked by ↓+↑, idle socket owners omitted. Before "show more" the card lists every program whose curve averages over 10 KiB/s across the last minute (`traffic::recent_average` — the mean of the readings, not of time; `SHOWN_FLOOR` / `AVERAGE_WINDOW`), never fewer than three (`MIN_ROWS`, filled by the next-highest averages) and with no cap above: the fixed preview of six filled with keep-alives whenever nothing bigger was running. The average picks the rows, the live ranking orders them. The read is ~3.5 ms, so the card samples every 2s while the Network tab is on screen (`TRAFFIC_REFRESH`) and every 10s otherwise (`TRAFFIC_BACKGROUND`, hidden panel included). The two clocks do not stack. The baseline and the ring survive hide, and a late answer is applied even if the tab has since closed — a diff across hidden hours was the reason the baseline used to be dropped, and the 10s read is that diff. Each row draws one ↓+↑ line instead of the two bars (`CurveBook`, up to `CURVE_WINDOW`, 10 min), in a 22px inset well like Overview's charts — on the bare card a quiet program's flat 0 read as a row divider (14px was tried: about 8px of swing inside the well, a burst indistinguishable from noise). Y is that row's own peak with the 64 KiB/s floor, so housekeeping stays flat and a busy program shows its own shape; X is the book's real span, stretched to the width and labeled with that duration (`40s`, `9m`, `10m` once full). A true zero connects, so a program that went idle draws down to the axis — and once a program has a line, every sample it cannot price draws 0 too (`CurveBook::record`): a counter that fell (the per-pid total is over the sockets open *now*, so it falls whenever one closes — routine for a tunnel or a browser helper), a reused pid, a pid with no baseline yet, the program gone from the table. Each of those used to be a break, and such programs drew as scattered dashes that read as missing data. Only time breaks the line: a gap longer than 25s between samples (`CURVE_GAP` — two missed 10s reads, or a sleep at its real width). It was 15s, and every background read landed 15s apart plus a few ms: the read rides the collector tick and was gated on when the last read *finished*, so the tick exactly 10s later saw 9.99s and the read slipped to the next tick (measured on the installed app as CPU bursts 15–16s apart) — a hidden panel's curves came back as dashes. `state::traffic_due` now lets a read run up to `TRAFFIC_SLACK` (1s, under the shortest tick) early. A series starts only once a program has moved bytes — before that it is drawn flat at 0 from the card's left edge, since it was quiet or absent either way — and it is dropped once the window holds no positive point. A transient read error keeps the ranking, the baseline and the curve, and warns once per message; `Restricted` (a bare `cargo run`) still shows the installed-app sentence and clears both. Linux is TCP only (`traffic.tip_linux`). These counters are not the interface totals — macOS `rxbytes` counts more than payload — and the card does not add them up to check.

**Config is shared with the zstats CLI** via `zstats::settings::default_dir()` (`~/.zstats`). The settings window (footer gear and title say Settings; the page that edits `config.toml` is still Config — a settings session must not die to the popover's auto-hide; `open_settings_window` in main.rs, reuse-or-rebuild) writes through `zstats::settings::apply_add` (same keys as the CLI's `-add`) then either `metrics::request_reload()` → `Monitor::reload_settings()` for `[alerts]`, or `metrics::request_rebuild()` for `[collector]` / `[daemon]` — those are baked into `LocalCollector` at construction, so the first sample after a rebuild legitimately reads `—`. Running `zstats serve` alongside this app double-collects; there is no detection for it.

**The alert template is the second file the Config page writes into `~/.zstats`** (`alerttpl.rs`, the card under the thresholds). zstats compiles in a per-platform table of raised bars for processes that are busy or large by design and reads `~/.zstats/template.toml` instead when it exists — wholesale, never layered — and its own comment says the fetching belongs in a client, not "inside a local metrics collector". So this app fetches `templates/alerts-<os>.toml` from the **zstats** repo's `main` (not this repo's assets, not a tag: the format version moves rarely and the contents move often, so a tag could never find an update). It does not bend the hard rule below — writing this file is the same act as `apply_add` writing `[alerts]`, and every threshold is still evaluated by zstats. Three things make it safe and all three are load-bearing: a user override outranks the template, so an update can never overwrite an Alerts-tab edit; `Template::parse` validates version, tables and every matcher key *before* a byte lands, so this app never writes a file that would make `reload_settings` start failing; and an update whose thresholds equal the compiled-in table writes **nothing** — creating an override identical to the built-in would pin the machine to today's table and silently outrank every future crate upgrade. A refused override is reported as its own state (`Source::Broken`) rather than as the built-in, because zstats then applies no `[alerts]` change at all and the Alerts tab would otherwise just look broken. A silent probe (`alerttpl::silent_check`, riding the updater's two-day clock in one background pass — one rhythm of unprompted network for the whole app) fetches the published table to *compare only* and lights the settings gear's shared dot when a clean, applicable, different table is waiting; **applying stays behind the card's button**, because this table decides what alarms and a schedule that applied remote content would be remote control of the alert engine. The dot ignores rewordings (threshold fingerprint, not bytes), never points at an inapplicable table (version-mismatch stays silent — the updater's own dot covers a release), and can be waved away per content (`template-check.toml`, display-layer only like the updater's skip).

**UI preferences (language / theme / tray face) live in `~/.zstats/app.toml`** (`prefs.rs`), edited from the settings window's Interface page. `keep_awake` lives there too and is the one key that acts on the machine rather than the panel — `awake.rs` below. The tray face (`tray.rs`, `face_for`) is Auto by default: CPU until `state::memory_needs_attention` says memory is the thing, or `state::disk_needs_attention` says a disk is — a live, undismissed episode this session. Memory wins if both are on. Memory-class episodes (process, app, or kernel pressure) must also pass `state::turns_the_face`, which is all of them except **pressure at the warning tier**: a memory-heavy Mac sits at warning as its steady state (zstats says so in the pressure rule itself and makes that tier wait 5× as long to report), and a face that spends half the day on memory has stopped being a signal — the card and the banner still carry it, only the menu bar waits for `critical`. The gate reads zstats' own `severity()`, never a raw `pressure_level`, and it is per *kind* rather than a blanket severity check because process and app memory episodes are Warning by construction upstream — gating the class would have deleted the face's original job. Then a memory stick with the memory still *available* (not used% — macOS runs high-used by design; available is what actually falls). A disk-full episode wears a disk glyph with that volume's available bytes (same leftover-not-used% choice); `disk_event_holds` is the same carve-out as `memory_event_holds`, against the event's own used-% bar. A volume that was ejected or is no longer listed gives the face up at once (`disk_volume_present`): the clock still runs, but with no volume to name the menu bar otherwise wore a disk over `—` for the whole recovery window. Disk is Auto-only — it does not grow a third status item. Turning *on* is display of a verdict zstats already made — it deliberately does not read the raw `pressure_level` off the sample: that level flaps, zstats' pressure rule debounces it (5 min to report, 5 min to clear), and the face must not turn before the banner would. Turning *off* is dismissal, or 5 minutes (`TRAY_RECOVER`, mirroring `PRESSURE_REARM`) of the episode holding under **its own recorded bar** (`memory_event_holds` / `disk_event_holds` — the only places in this app that compare a live figure to a threshold; bounded to the event's own line, zstats' own fields, and the tray face alone — the card and tab tint stay until dismissed or the day turns; it exists because the engine never says "recovered", so the face otherwise stayed memory until a manual dismiss). `both` keeps two status items: AppKit inserts a new item to the *left* of existing ones, so the second (built on demand, dropped to remove) wears CPU and the primary wears memory. Swapping the icon must go through `set_icon_with_as_template(…, true)` — plain `set_icon` drops template mode on macOS and paints the alpha-only glyph as a black block. A live `AlertEvent` that lands while the Alerts tab is not on screen lights a corner spec on the primary face — extra alpha on the same template, same ink as the glyph (white on a dark menu bar); a coloured spec would have to drop template mode, which is a black block on a dark bar. It is display of "you have not opened that list", not a second threshold: restored (`live = false`) cards do not count, looking at Alerts (tab switch, or revealing the panel while already on it) clears it, and a follow-up of an episode already seen re-lights once they look away, the same way it would a banner. Every Auto face carries a dotted template because Auto can be wearing the memory stick or the disk when the report lands. Deliberately not in config.toml: `zstats::settings::save` serialises only the sections the CLI models, so any extra key there would be dropped on the next `apply_add` round-trip. A forced theme also pins `NSApp.appearance` (`apply_ns_appearance` in `main.rs`) so the vibrancy material follows it; a language switch rebuilds the tray and app menus, which snapshot their translated titles at build time. **The Omarchy theme** (`ThemePref::Omarchy`, `omarchy.rs`) paints the desktop's current Omarchy palette — `~/.local/state/omarchy/current/theme/colors.toml`, legacy `~/.config/omarchy/current`, both formats, Tokyo Night on any failure, all as huacnlee/gpui-omarchy reads it — but through our own loader, not that crate: it is a component library pinned to `gpui-kit =0.7.0`, and it and gpui-component would both own gpui-base's global colours. It is offered only where that directory exists, plus every debug build so a Mac can try it on the fallback (`omarchy::selectable`); a stored `omarchy` anywhere else reads as System (`crate::theme_in_force`). Every token derives from the palette (`theme::OmarchyTokens` — neutral steps from background toward foreground; the palette's accent is the theme's `mark`, the role Golden's champagne plays; the alarm is the palette's red), light or dark is the theme's own rather than the window appearance, and gpui-kit's widgets get a theme generated from the same palette (`theme::omarchy_theme`) under a colour-fingerprinted name — `ThemeRegistry::load_themes_from_str` skips a name it already holds, so a fixed name froze the session's first palette. Re-read when the panel opens (`refresh_omarchy_palette`; restyled only if it changed), never watched.

**zstats owns both the alerts and the numbers. Treat this as a hard rule.**

- **Alerts.** Every `AlertEvent` is produced by zstats' rule engine from the thresholds in `~/.zstats/config.toml`. This app evaluates no alert condition of its own. `state/alerts.rs` only merges incoming events into episodes keyed by `(subject, kind)`, caps the list at 20, lets a card be dismissed (display-layer only — a condition that still holds re-opens it on the next report), retires episodes once the local day turns, and mirrors the list to one file per local day, `~/.zstats/alerts-YYYY-MM-DD.toml` (`alertlog.rs`, 30-day sweep), so today's episodes survive a restart and the past week is readable on the tab — memory, never a re-evaluation: nothing is re-delivered as a banner, and a restored episode is simply the one a re-crossing merges into; a dismissed card is written back with `dismissed = true` rather than dropped, because the week's record must say what fired, and the past-days block is read-only (launch / tab entry / day turn — never per frame); the Alerts tab edits thresholds through `zstats::settings::apply_add`, so the panel and the CLI can never disagree about when something fires. The same editor is reachable from the Processes and Apps expansions (`processes::threshold_editor`, one chip row per rule under the bars those pages already display) — until then a threshold could only be tuned while an alert was *on screen*, so the moment to say "this one may run hot" was the moment it had just interrupted you. It sits under the bars rather than beside the Quit button because a subject has *two* thresholds and one button in a shared action row cannot say which it edits. The Config page's overrides card is the set of those per-subject rules, read back and revocable (`override_rows` flattens the five maps; `state::remove_alert_override` → `apply_remove` drops one line) — writing an override from a card while the only way out was hand-editing config.toml made personalisation a one-way door, and the counts on the thresholds card said twelve programs were tuned without saying which. A new alert belongs in zstats' rule engine, not here. Three delivery-layer filters sit on top, and none bends this rule — all filter *banners* while the engine keeps evaluating, the list keeps recording and config.toml stays untouched. The **master switch** (`prefs::notifications`, the Interface card's toggle in app.toml) turns banners off entirely — recording-only mode; it sits ahead of the other two so an off period records no interruptions into their clocks, the log writes `banner="muted"`, and the Alerts tab's Watching list plus a swapped footer note say so on-screen. The **snooze** (`snooze_banners`) is the one the user asks for, bounded by a deadline. The **auto-quiet** (`banner_damped`) is automatic: an episode that has already interrupted `NOISY_AFTER` (2) times inside `NOISY_WINDOW` (1h) stops producing banners until the window slides past those deliveries. It exists for a subject that keeps crossing, clearing and crossing again — zstats already spaces the reminders *inside* one episode (the pressure rule backs off 30m/1h/2h/4h), but a flapping subject opens a fresh episode each time and each one arrived as news. It is per episode on purpose: a different subject crossing its line is different information and still arrives. Both wear a pill on the card, because a banner that silently stopped arriving is indistinguishable from a rule that stopped firing; "Resume" clears both, and both are gone at the next launch — unlike the list beside them.
- **Metric values.** Every raw figure the UI renders comes off the `Tick` — `snapshot.*`, `process_stats` (the rolling averages), and `records::read_range` for History. Do not recompute a number zstats already reports, even when the inputs are sitting right there: `views/disk.rs` deliberately renders `DiskSnapshot::used_percent` instead of dividing used by total, because a locally derived figure could only ever disagree with what the CLI paints and what the disk alert fires on. Views format and colour; they do not derive. The exception zstats itself specifies is `traffic::diff`: `process_traffic()` returns cumulative socket bytes and tells the caller to subtract two calls. That diff is the rate; it is not a number the snapshot already carries.

The one carve-out is `watch.rs`, and it is about *what question is asked*, not about a second source of numbers — it still reads zstats' own fields (`cpu_time_ms`, network snapshots). Its three observers — sustained low-grade CPU (integrated from `cpu_time_ms`; the rule is `watch::SustainedRule` — bar = `alert-cpu ÷ sustained_divisor`, held for `sustained_hours`, both from `app.toml` with defaults 3 and 2h, built from prefs on every question so a picker change is live on the next tick; a divisor rather than a percent so the bar keeps following `alert-cpu`), abnormal processes, interface activity — exist because zstats structurally cannot see them: sustained load never crosses a threshold by definition, zombies are ranked out of the process table before the UI sees it, and the kernel's cumulative network counters cannot say *when* bytes moved. None of them is an `AlertEvent`; of the three, only sustained load reaches the notification centre, deliberately as a silent banner (`notify::post_sustained`), and that banner's click lands on a read-only card in the Alerts tab — display of the watcher's state, never a rule. `trend.rs` is a fourth observer of the same class: an hour of per-tree CPU minutes (60 × u16 percent-of-one-core, minute-max, keyed by tree name, ~20 KB total) behind Overview's "climbing this hour" rows. It exists because a rate has no memory — the snapshot cannot tell "always 30%" from "was 2% ten minutes ago" and zstats' rolling averages reach back only 60s — and it keeps two kinds of absence distinct: an unreported minute (asleep — excluded from the comparison) versus reported-but-below-the-collector's-cap (genuinely quiet — counts as zero *for CPU*, which is what lets a tree climbing out of nothing register the full climb). That second rule is CPU-only and `climb` deliberately breaks it: the groups table is a CPU ranking capped at `max-processes`, so falling out of it is evidence about CPU and nothing at all about a footprint — zero-filling those minutes fabricated a climb the size of a tree's whole memory (measured: a terminal drifting in and out of the top 50 announced as "up 1.1 GB · holding 1.1 GB", the two figures identical). Display only: a climb fires nothing, the rise tag stays muted (accent is for thresholds), and `RISE_FLOOR` in `overview.rs` gates which climbs are worth rows. The same ring is fed a second time with each tree's footprint in MB (`state.mem_trend`) for the leak question — `trend::climb` is newest-five-minutes against the earliest-reported-five, only while the tree is still at its high, and only after 20 reported minutes; the memory card's `mem_climb_strip` names climbers past `MEM_RISE_FLOOR`, and a climb past `trend::CREEP_NOTIFY_BYTES` (1 GB) posts one silent banner via `notify::post_memory_creep`, re-armed by the clock (`trend::CREEP_REARM`, one ring length) and never by the figure — re-arm-on-dip was tried and a GC sawtooth crossing the bar became three Chrome banners in 29 minutes; while that banner is out the climb also holds the Alerts tab's second read-only card (`state::creeps_active`, same pattern as the sustained card), because every banner's click opens that tab and must land on its subject. History's third sort lens (`Spender::memory_growth_bytes`, last recorded footprint minus first) is the day-scale form of the same question, read straight off zstats' records. `active.rs` weights both slow-burn banners rather than producing one: an `NSWorkspace` `didActivateApplication` observer (event-driven, no polling, no entitlement — the app is in `userInfo[NSWorkspaceApplicationKey]`, *not* the notification's `object`) keeps a bounded pid → last-frontmost table (entries cleared on `didTerminateApplication`, because a recycled pid must not inherit a dead app's stamp), asks the *current* frontmost at question time (activation fires on app switch, so an app used for hours without switching away would otherwise read as untouched), and `notify::unused_clause` appends "Not used for 3h" past `UNUSED_AFTER` (1h) — the line that separates a finding from a false alarm, since the same load in the app you are typing in is work. A pid this session never saw come forward is *no answer*, never a long idle: a banner may say less, never claim a stretch the reader cannot check. `procscan.rs` is the sole place that queries the OS directly (`sysctl(KERN_PROC_ALL)`), and it reports process *state*, not metrics. `watch.rs` touches no gpui types precisely so it can be tested against hand-built sample sequences. `assetinfo.rs` is the same posture applied to system files: the whole-disk scope surfaces multi-gigabyte `AssetsV2` rows whose names say nothing, and rather than a hand-written table of what each asset type is (which `cleanhints` forbids — its entries come only from each tool's own documentation, and Apple documents none of these), it quotes each asset's own `Info.plist` — type, `__RequiredByOS`, `__AssetDefaultGarbageCollectionBehavior`, `AssetLocale`. Same shape as the `CACHEDIR.TAG` rule (*the owner declared it*) and the same restraint: a declaration earns a sentence, never a delete button, because `mobileassetd` owns that content. Unanimous readings only, capped at 8 plists per row — a verdict from a sample would be a claim about assets nobody looked at. `diskscan.rs` (the disk-space window's directory analyser — see docs/disk-analysis.md; physical blocks like `du`, a hard-linked inode counted once under the first name the walk meets (`shared_links` — a pnpm store and the node_modules linked from it were counted twice), APFS clones still per appearance because `ATTR_CMNEXT_PRIVATESIZE` measured as a lower bound costing 2–5× the walk for a 4 MB difference in 11 GB of caches) is the same class of one-shot panel-owned OS query, with one deliberate deviation: its minutes-long walk **survives every surface it is shown on** — panel hide and the window's own close alike; only the explicit cancel stops it, because a hide-reset would mean no analysis ever completes. The run lives on its own thread and reports progress and completion exclusively over a channel, run-id-guarded so a superseded run's events land nowhere. Opening a directory row expands it in place rather than re-rooting the card (`state::toggle_expansion`): the finished scan's retained index answers instantly wherever it recorded anything, and only folded leaves and all-small interiors take a sub-walk — one at a time, same channel and run-id shape, landing in `expanded` instead of replacing the result on screen. **`diskwatch.rs` is the analyser's one scheduled run** ("what grew this week", the question "what is big" cannot answer): once a home walk has finished by hand — so any one-time folder consent is already answered and a background walk never raises a prompt — `state::maybe_check_disk` re-walks home once `CHECK_EVERY` (24 h), only on power (`battery.state` not Discharging), under `BUSY_CPU`, with neither the panel nor the disk-space window on screen, at `diskscan::Pace::Background` (a serial walk on one thread at background QoS — throttled CPU and I/O on macOS, nice 19 on Linux); a user's walk cancels it. Every finished home walk, theirs or the check's, writes one per-day snapshot (`~/.zstats/disk-history/YYYY-MM-DD.toml`, directories ≥ `RECORD_FLOOR`, 14 days) and growth is read from those files alone (`latest_report` — the newest against the one nearest a week before it), so a launch can show it before any walk; the deepest directory carrying a climb is its row (`DOMINANCE_PERCENT`), a climb past `NOTIFY_BYTES` (5 GB) posts one silent banner per directory per week (`notified.toml`), and the Alerts tab's read-only card is its landing spot. Display and a quiet banner, never an `AlertEvent`. FSEvents was measured and rejected for this (2026-10-02, module doc): a day of history under `$HOME` was 2.1 M events and 199 s to replay against a 25 s walk. `prefs::disk_watch` (on by default, `disk_watch = false` to stop) is the switch on the analysis card. **`dupes.rs` is the window's third question** ("what is stored twice", its Duplicates tab, state in `state/dupes.rs`): length, then a BLAKE3 of the first 64 KB, then the whole file — only for what the pass before could not rule out. It walks on its own rather than reusing the analyser's walk (that one keeps a counter per directory and no file list, by design), with the analyser's lifecycle (own thread, run-id-guarded channel, survives the window, only Cancel stops it, cancels and blocks the daily check) and no cache file. Home is `$HOME` at ≥ 1 MB; a picked folder is searched the moment it is picked, every non-empty file. `~/Library` is left out unless it is what was picked; never descended (`dupes::skips_dir`): hidden directories, `CACHEDIR.TAG` trees, every directory `cleanhints` names (measured: Go's read-only module cache was a third of a developer's groups), a `vendor` beside its manifest, packages — inside those a "copy" is a tool's or an app's, and trashing one breaks the whole. The analyser's exclude list is deliberately not applied: it lives on another tab and would be a filter nobody can see. "Can be freed" is honest about storage: every file is listed once per `(dev, ino)` (a bind mount shows one file at two paths with nlink 1 — "trash the other copy" there deletes the only one), a file with other hard-link names frees nothing (`DupeFile::linked`), and APFS clones are grouped by `ATTR_CMNEXT_CLONEID` and counted once.

The app *acts* on the system in exactly two places, both click-plus-confirm, both delivering refusable or recoverable requests (a third, lighter touch — the keep-awake assertion — is described after them). `bigfiles::trash` is Finder's own move-to-Trash (`NSFileManager.trashItemAtURL`, never a direct unlink) behind the disk-space window's large-file rows, its duplicate rows and the analyser's regenerable-cache rows. Duplicates go one copy at a time, never in bulk; every listed group has two copies or more, and `DupeGroup::spare` re-checks the disk right before the move (this copy and another still have the length and modification time the search saw), because the list is a photograph — an edited copy is no longer a duplicate, and one deleted since must not make the last copy look spare. Regenerable caches go only for signature-checked `CACHEDIR.TAG` trees and caches their own tool's documentation lists (`cleanhints` `trashable`), per-row or in bulk, never for heuristic or plain directories. The bulk confirm is a tickable list of every row it would move, with sizes (`confirm::ask_pick`) — the one-line "N items, ~X GB" sheet asked for trust in a number. Every row says what its standing rests on (`basis_pill`: "rebuilds" for a TAG tree or a documented cache, "manual" for a known owner whose content it does not simply rebuild), because only TAG rows used to wear a word and 31 documented caches beside one read as unexplained — except in the suggestions, where every row rebuilds itself: the section title says so once, the basis moves to the name's tooltip, and only exceptions ("running") stay pills. A cache whose app is running (`cleanhints` `app` — a bundle id or a vendor prefix, read from the app's own Info.plist; `active::running_bundle_ids`) wears "running", says so in its confirm, and starts unticked in the bulk sheet: a live app keeps writing into the moved folder, so the move frees nothing until it restarts. Once anything has moved, one line above every tab says the space returns only when the Trash is emptied (`trashed_note`) — its button opens the Trash and never empties it, the one irreversible step staying the user's own. `terminate.rs` is the other, and it stays strictly on the "how" side of the rule. It serves two callers. The quit button on memory alert cards consumes zstats' `AlertEvent` (deciding *when* something is over the line stays in the rule engine) and calls `request_quit` — a refusable request, `NSRunningApplication.terminate()` (⌘Q-equivalent) for applications, SIGTERM for bare processes. The Quit control on a process row calls `request_term`: SIGTERM only, never the app-level tier, because a row is a process and promoting a bare pid to an app quit would act on more than the row names. The listening card's Quit is the same SIGTERM through `request_term_named`, which first checks the pid still carries the name the row showed (`still_named`, the check `request_quit` makes) — that list can be 15s old — and it is offered only on a row that stands for exactly one named process this user may signal (`listening::quit_target`): `redis-server ×17` is seventeen processes, and a search narrows `×N` to the holders of what matched, which is how one of them gets its button. Neither ever sends SIGKILL. Both guards live here too — `can_quit` (the kernel's permission check) and `can_term` (the policy one: never pid 1, never ourselves) — so a control that cannot work is never rendered, and the delivering end re-checks anyway. Only ever behind a user click plus the `confirm.rs` sheet; nothing is evicted automatically. **Two gates decide whether that button exists at all**: `kill(pid, 0)` (can this user signal it) *and* `SeenAlert::live` — the episode must have been reported in *this* session. The second gate exists because the alerts list now outlives the process: a card restored from this morning names a pid, and after a reboot macOS hands low pids straight back out, so a stale card's quit could deliver SIGTERM to whatever holds that pid now. `can_quit` cannot catch that — it answers "may I signal this pid", never "is this still that program". Restored cards are records to read (they wear an "earlier session" pill); the Processes tab still offers a quit for anything actually running. The updater reaches two hosts, not one: GitHub first, then the Gitee mirror the release workflow copies every tagged release to (`GITEE_API` in `updater.rs`, `publish.yml`'s `gitee` job) — for networks that cannot reach GitHub at all, where the check would otherwise only ever fail. The mirror carries the *same files*, `SHA256SUMS` included, so the digest that vouches for a download is unchanged no matter which host served it; a mirror is a second address, never a second build, and never a second trust assumption. `updater::install` is the bounded exception to the two-place rule: behind the user's download-and-install click it rewrites exactly one thing — the app's own bundle — after checking the mounted image carries our `CFBundleIdentifier`; the old bundle is renamed aside into temp (never deleted while the process running from it lives), and every blocked step — bare binary, unwritable target, foreign bundle, failed copy (rolled back) — degrades to the old open-the-DMG drag flow with a log line, which is why `install` practically cannot fail. The finished install offers a restart (`updater::relaunch`: a detached `sh` waits for this pid, then `open`s the bundle — the fallback keeps the old quit-to-install caption instead). The in-place path detaches its own image; `sweep_installer_mounts` at launch stays as the backstop for busy detaches, fallback installs and older builds' leftovers.

**The keep-awake switch is the third touch, and deliberately not shaped like the other two** (`awake.rs`, the Interface card's switch). It holds one IOKit power assertion while it is on and drops it the moment it is off. No confirm sheet: it changes nothing on the machine, a second click ends it, and it cannot outlive the process — the kernel drops an assertion when its holder exits, crash included, so nothing releases it on quit. `PreventUserIdleSystemSleep` (what `caffeinate -i` takes) rather than `PreventSystemSleep`, which is only honoured on AC — a switch that silently stops working on battery is worse than no switch. Display sleep and the lid are deliberately left alone (no assertion outranks the lid) and both limits are named on the switch's tooltip, because each otherwise reads as a bug. It is the one preference that acts on the machine rather than the panel, so it is re-applied at launch from `prefs::keep_awake` — and since a Mac that will not sleep has to be able to say why, the footer wears an indicator while it is on (clicking it turns the hold off), both transitions are logged at INFO, and the assertion carries `APP_NAME` so `pmset -g assertions` names us.

There is exactly one place the panel shows a machine state ahead of zstats, and it is bounded on both ends: after `diskutil eject` **returns success**, `state::mark_ejected` withholds that volume's card until a snapshot agrees (or `EJECT_HIDE_MAX` passes, for a drive replugged onto the same path). It exists because zstats serves the whole disk list from cache between refreshes — at the panel's 15s `disk_io_refresh_interval` the card outlived the drive by up to a full cadence, and waking the collector does not help since that cadence is wall-clock. The entry point is an authoritative OS result, not a guess; anything less certain does not get this treatment.

A disk `AlertEvent` for a **read-only extra volume** is dropped at ingest (`volflag::skips_disk_alert`: `/Volumes/…` and `statfs` `MNT_RDONLY`) before the list or a banner sees it. A DMG is sized to its contents, so 99% / 0 GB free is the packaging, not a disk running out, and nothing the user can do will free space on a volume the kernel has marked read-only. The `/Volumes/` gate is load-bearing: on Apple Silicon `/` itself is `MNT_RDONLY` (the sealed system volume), and skipping every read-only mount would swallow the boot-disk alert. sysinfo already knows the flag; zstats' `DiskSnapshot` does not forward it, so the engine cannot skip these. Fail-open if `statfs` fails — a volume we cannot inspect still alerts. Writable USB disks keep firing. This is not a second threshold: the engine still evaluated; we refuse a condition that cannot be acted on, and the skip is logged (`banner="skipped"`) so the trail still says why nothing popped up.

The `HOT_*` / `FULL_PERCENT` / `CORE_HOT` constants in `views/` are the only thresholds allowed to live in this repo, and they change colour only — they never produce an alert or a notification. A process row's colour has a second input beside `HOT_PERCENT`: `watch.rs`'s sustained-load state (`processes::is_hot`), because a long low-grade hold never crosses a line by definition and the burst rule alone left it looking idle. Same restriction — the colour is display, the watcher's own notification is separate, and both pages read the one rule so a pid is red in both or in neither.

**Window model.** The panel is created once and shown/hidden/moved through AppKit directly (`window_ext.rs`), bypassing gpui's create-or-destroy model, which leaks ~1 MB per cycle here. On Wayland none of that applies: a client cannot position a window, so the panel is a wlr-layer-shell surface (`panel_kind` in main.rs) anchored top-right by the compositor, and hide is a destroy with the collector pace dropped by hand — `docs/omarchy-port.md` is the port's record, including why the tab shortcuts bind `secondary-` rather than `cmd-` (gpui reads `cmd` as Super off macOS, and Super belongs to Hyprland). `setFrameOrigin` / `orderOut` must run in `after_app_borrow` (main-queue hop), not inside the tray's `cx.update` and not in `cx.defer`: they fire `windowDidMove` synchronously, and gpui's handler `try_borrow_mut`s the App — `ERROR gpui::window: RefCell already borrowed` on every tray click if that cell is still held. Repaint is gated on `CollectorPace::is_visible()` — the window is moved off screen, so gpui would otherwise keep rendering it. The panel handle lives in the store with the other two; `cx.windows().first()` is SlotMap order, not "the panel", and would `orderOut` the wrong window. **Two ordinary windows sit beside it**: settings (`open_settings_window`) and disk space (`open_storage_window`, `views/storage.rs` — three tabs: the directory analyser, large files, duplicates; the selected tab lives in the store as `StorageTab`, each tab keeps its own `ScrollHandle` in the window, and ⌘1–3 / ⌘R switch and re-run. Nothing in the window scrolls but a card's result: the strip and each card's header and toolbar stay put, and the result scrolls inside the card's border under an overlay scrollbar (`storage::tab_card` — natural height while it fits, shrinking to the window's bottom margin when it does not; the drawer stays with the toolbar that opens it). No tab repeats the boot volume: a band of it on every tab was tried and removed — a fifth of the window's height for a figure the panel's Hardware card already shows, and one a cleanup does not move until the Trash is emptied. The window has its own type scale (`META_PT` / `ROW_PT` / `HEAD_PT`, 10/12/13), every path is two runs (dim folders that truncate first, the bright name kept — `path_label`), every row reserves the same two trailing `action_slots` so sizes share one right edge — resting at `ACTION_REST` opacity until their row is hovered, so thirty identical glyphs stop out-shouting the figures — share bars are 2px in the dimmed ink (an opened row's children measured against that row, not their largest sibling), a finished analysis is a directory map rather than a table (`storage/dirmap.rs` over `squarify::layout` — one level as a squarified treemap, the level under each tile drawn inside it when the tile is large enough, a click opens a tile and the path above goes back; levels come from `DirIndex::children_of`, a children map built once with the index because the map asks every frame, and where the index cannot answer — a result restored from its cache, a folded tree — from the same one-at-a-time walk a row's expansion takes; the remainder of a level against `ScanResult::total` is one "files and small folders" tile; colour keeps neighbours apart and says nothing about size — every folder tile wears one of `theme::map_hues` (five per scheme, every pair checked against the dataviz rules on that scheme's surface: ΔE ≥ 15 normal, ≥ 8 under each colour-blind simulation; Omarchy lends its palette's accent, yellow and green unvalidated), assigned by `squarify::colour` so no two tiles sharing an edge match (a depth-first search, largest tile first, least-used hue first; five always colour a planar map), only the remainder is `theme::map_rest` grey — three hues with a grey tail was tried and read as unfinished; no red or orange, which would read as the alarm; labels black or white by tile luminance; the map sits beside the lists when the window is at least `SIDE_BY_SIDE_MIN_W` wide and above them otherwise; it replaced the big-directories table and the composition bar), large files carry their modification date, a duplicate group marks its oldest copy only when the dates tell the copies apart (`DupeGroup::oldest`), and a tab before its first run is two sentences and the theme's primary button (`empty_state`) — the mark, never the alarm red). Settings opens at `SETTINGS_WINDOW_SIZE` (507×620); disk space opens zoomed to the screen's visible area (`window.zoom_window()`, menu bar and Dock kept), because a map is read by area, and the zoom button returns it to `STORAGE_WINDOW_SIZE` (720×480 — wide rather than tall: what it lacked at 507 was width for paths, and 720×840 stood nearly the full height of a 14-inch screen). Sizing it to its content was rejected: once run every tab outgrows any cap, so the window would only resize in the empty and running states — growing when a walk lands, shrinking on a tab switch. Both floor at `AUX_MIN_WINDOW_SIZE`, which must stay under both opening sizes or the minimum silently widens the window. Both are plain gpui windows with real title bars, reuse-or-rebuild through a handle in `state.rs`, Esc/⌘W via one `CloseWindow` action bound in two `key_context`s. Disk space observes the store (scan progress). Settings does not follow the collector tick: it compares `settings_paint_token` (prefs epoch, config.toml, update/template/hints fetches) and probes Full Disk Access on Permissions entry and window activation, not per frame. Both exist for the same reason: the popover auto-hides on any focus loss, and neither a settings session nor a minutes-long walk and its three ranked tables can live on a surface you cannot look away from — and 320px could not show the tables either, which is what the disk window's width buys back.

**Vibrancy is three layers, and each has exactly one job — do not shift work between them.** Bottom: gpui's `Blurred` backing is an `NSVisualEffectView` *subclass* that pins the `Selection` material and strips the layer background on every `updateLayer` — deliberately colourless, i.e. **pure blur with no luminosity clamp**, and any material set on *that* view is stripped the moment AppKit repaints (this is why a white wallpaper once arrived at full brightness). Middle: `use_popover_material` (main.rs) therefore inserts a **stock, unsubclassed** `NSVisualEffectView` above gpui's blur view and below its Metal layer — `.popover` material, behind-window, active, re-entrant via `isMemberOfClass` — whose clamp is the *protection*: the reason system menus stay dark over any desktop. It clamps pure white only to mid-grey, which is why the top layer still exists. Top: the root wash (`BACKGROUND_OPACITY_DARK` = 0.35) *finishes* what the clamp leaves — measured: 0.55 (the raw-blur era's defence) stacked on the material reads fully opaque and kills the glass; 0.20 lets dim captions wash out over white; `HUDWindow` was tried for a darker clamp and reads *lighter* on current macOS. Light mode concedes the effect (0.80 wash) — vibrancy there is pale-on-pale. Because the ground is guaranteed by the middle layer, cards stay translucent lifts (`theme::surface`, dark `0xffffff12`) — making them solid was tried and reverted (it fixed white wallpapers by deleting the glass everywhere, then collided with black ones); what that detour left behind and must stay is the hairline outline in both themes (`widgets::outline`). Full history in `docs/design.md` under 毛玻璃.

**Startup order in `main()` is a constraint, not a style choice**: `dock::suppress_regular_policy()` before the run loop; `gpui_kit::init` before any component; `prefs::load()` before the theme and locale it feeds; `apply_appearance` before the first frame; `i18n::init()` before the first `t!`; `set_quit_mode(QuitMode::Explicit)` before anything can close a window.

## Conventions

- **Module paths**: cross-module *functions* are called with one level of qualification — `use crate::diskscan;` at the top, `diskscan::save_cache(...)` at the call site. Never inline `crate::diskscan::save_cache(...)` in a body, and never import bare function names (the module prefix is what tells a reader in `state.rs` whose side effect this is). **std follows the same rule** with its module as the level: `use std::fs;` then `fs::write(...)` — never `std::fs::write(...)` inline (the Book's idiom; `std::os::*` trait imports stay block-scoped as they are). *Types and constants* are imported directly (`use crate::diskscan::{self, ScanResult}`, `use std::time::Duration;` — fold the module in via `self` when both are needed); imports used only by tests live inside the `mod tests` block, not at file top. Crate-root items (`crate::APP_NAME`, `crate::open_settings_window`) stay fully qualified: there is no module level to keep. Non-std external crates keep their crate-name paths (`smol::channel::unbounded`, `zstats::settings::apply_add`) — there the crate prefix is the provenance.
- **Wide parameter lists become structs.** When a function trips clippy's `too_many_arguments`, group the parameters into a named-field struct (`AnalysisRow`, `Aggregates`) instead of adding an `#[allow]` — the lint is right about the call sites, and named fields are what fix them.
- **Comments explain why, not what.** Module-level `//!` docs carry the reasoning, and most constants have a doc comment justifying their value (often with measured numbers). Match that — a new tunable without its rationale is out of place here.
- **Threshold colouring goes through `theme::fill_for()` / `theme::text_for()`**: neutral `ink` until over the line, brand `accent` after. Don't hand-pick colours for this.
- **A theme switch changes paint, never geometry.** Anything gated on `theme::is_dark()` may vary colour, shadow or opacity only — never borders, padding, sizes or font metrics. gpui borders occupy layout space (taffy box model), so a light-only `border_1()` once made every light card 2px taller than its dark twin, and a window sized snugly under one theme scrolled under the other. Card outlines in both themes go through `widgets::outline` (a zero-blur inset `BoxShadow` in `theme::border()`'s ink, which costs no layout) — any future theme-conditional chrome follows that pattern, and dark/light must stay pixel-identical in element heights and positions.
- **Custom SVGs go through `assets::CustomIconName`**, never a raw `Icon::empty().path("icons/…")`: the filename then lives in one place, `assets.rs` embeds an explicit allowlist (`#[include]`), and a test asserts every name resolves to an embedded file. Anything gpui-kit's `IconName` already has should use that instead of shipping another SVG.
- **Clickable things need a visible affordance** — hover fill, a border that lifts, or real button chrome. macOS keeps the arrow over every native control and reserves the hand cursor for links, so `cursor_pointer` appears exactly once in the app: the footer's GitHub button, the only control that opens something outside it. Don't put it on buttons, rows or tabs; see the affordance rule in `views/mod.rs`.
- **i18n**: `i18n!` is pointed at the empty `locales_stub/` on purpose; real strings live in `assets/locales/{en,zh}.toml`, embedded compressed and parsed lazily by `i18n_loader.rs`. Add every key to *both* files — a test enforces parity, because rust-i18n silently falls back and a missing key just shows one stray English string.
- **Cross-file invariants have tests guarding them**: `Cargo.toml` must keep declaring its `[package.metadata.bundle] identifier` (UN-based notifications attribute by the real bundle now, so nothing claims an id in code — but a bundle without one fails notification authorization at runtime with nothing pointing at the cause), and the tray icon rasterisation is checked for coverage (a parse failure yields a fully transparent bitmap and no error).
- **Dependency pinning**: GPUI is the crates.io `gpui-pre-*` family (`package = "gpui-pre"` so source still says `gpui::`), pinned to the same 0.3.x gpui-kit depends on. After any bump, `cargo tree -i gpui-pre` must show one copy — two identities in the tree is two GPUIs. Commit `Cargo.lock`.
- Measure CPU with two cputime samples over wall clock, never `ps -o %cpu` (a decayed average polluted by startup).
